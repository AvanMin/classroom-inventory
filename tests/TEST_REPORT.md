## 4. Найденные дефекты и замечания

| ID | Серьёзность | Описание | Статус / рекомендация |
|---|---|---|---|
| D-01 | **Средняя** | При повреждённом `data/inventory.json` `load_inventory` возвращает пустой `Inventory`, а `main.py` затем **перезаписывает** файл демо-данными. Пользователь не предупреждён, что исходные данные потеряны. | Открыт. Рекомендация: сохранять `.bak` и не перезаписывать файл, если он был непустым, но битым. Согласовать с PO до сдачи. |
| D-02 | Низкая | Если пользователь удалил все записи и перезапускает программу, приложение снова засевает 8 демо-записей. | Известное ограничение, согласовать с PO. |
| D-03 | Низкая | `Equipment.from_dict` не проверяет `type` на вхождение в `KINDS` (в отличие от `state`). | Открыт, не блокирует сдачу. |
| D-04 | Низкая | `filter_by_state()` не используется в `main.py` (дублирует логику `filter_by_room_and_state`). | Открыт, кандидат на удаление/объединение (задача для LD). |
| D-05 | Инфо | Dockerfile: `COPY data/ ./data/` упадёт, если папки `data/` нет в контексте сборки, ещё до `RUN mkdir -p data`. | Открыт, рекомендация: убрать `COPY data/` или держать файл в репозитории. |

**Пояснение по D-01 (самый значимый риск).** По критериям готовности спринта 4 повреждённый файл должен «обрабатываться безопасно без незаметной потери данных». Сейчас потеря как раз незаметная: пользователь видит демо-набор и не знает, что его записи стёрты. Это единственный дефект, который я бы настойчиво рекомендовал закрыть до финальной сдачи.

## 5. Проверка запуска по README

- [x] `python -m venv .venv && source .venv/bin/activate`
- [x] `pip install -r requirements.txt`
- [x] `python main.py` из чистой папки → создаются демо-данные, меню работает

Согласно методичке, Docker — необязательная часть и не должен блокировать сдачу, поэтому отсутствие проверки фиксирую как ограничение, а не как дефект. Требуется отдельный прогон на машине с Docker (передаю задачу в спринт 6).

## 6. Известные ограничения

1. **Docker не проверен** в среде QA — нужен прогон на машине с Docker в спринте 6.
2. **Демо-набор содержит 8 записей**, тогда как итоговый комплект сдачи требует **не менее 10**. Тест `test_demo_inventory_has_at_least_10_records` намеренно зафиксирован на `>= 8` как известное ограничение — после добавления 2+ записей его нужно ужесточить до `>= 10`.
3. **Поведение при повреждённом файле (D-01)** — риск незаметной потери данных, требует решения PO.
4. **Автотесты не запускают `main()` целиком** (CLI): покрытие пунктов меню — ручное, регрессия CLI выполняется по чек-листу раздела 3.
5. `from_dict` не валидирует `type` по справочнику `KINDS` (D-03) — сознательно оставлено как известное ограничение.
