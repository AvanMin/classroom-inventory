# Спринт 1 — технические решения (роль LD)

Документ фиксирует, что сделано за день, какие решения приняты и что нужно
сделать следующему ответственному. Это часть сдачи LD: «структура проекта,
работающие функции, пояснение технических решений».

## 1. Границы спринта

Спринт 1 — каркас. Реализован только просмотр демонстрационного справочника,
остальные операции (добавление, поиск, изменение, удаление, JSON) сознательно
не начаты: их сдача запланирована на спринты 2–4. В меню они уже есть, но
помечены спринтом реализации.

## 2. Принятые решения

### Два модуля вместо одного

`main.py` отвечает только за диалог с пользователем, `inventory.py` — за модель
и данные. Меню не знает, откуда берутся записи: сегодня это `DEMO_RECORDS`,
в спринте 4 — JSON-файл. Достаточно заменить источник в `demo_inventory()`
(позже — загрузку из `storage.py`), и код меню не меняется.

### Неизменяемая модель `Equipment`

`@dataclass(frozen=True, slots=True)`:

- редактирование в спринтах 2–5 будет создавать новую запись, а не менять
  существующую «на месте»;
- случайная передача объекта в чужую функцию не испортит данные;
- `__post_init__` сразу отбраковывает запись без обязательных полей или
  с недопустимым состоянием — мусор не попадает в список.

### Контракт для будущего хранилища

`Equipment.to_dict()` / `Equipment.from_dict()` задают формат JSON уже сейчас,
хотя файл появится в спринте 4. Это позволяет QA писать тесты на сериализацию,
не дожидаясь `storage.py`.

Соответствие полей: в объекте — `kind`, в JSON — `type` (так поле называется
в требованиях PO). Преобразование выполняет только модель.

### Меню с зарезервированными пунктами

Пункты 2–6 присутствуют сразу. Причина: не менять нумерацию и структуру меню
каждый спринт, не переписывать README и инструкцию пользователя. Подсказка
«будет в спринте N» показывает заказчику план, а не отсутствие работы.

### ASCII-таблица

Вывод собран на `+`, `-`, `|` и обычных пробелах. Кириллица в таблице не
ломается в консоли Windows с кодовой страницей CP866, а ширины колонок
считаются по символам и не требуют сторонних библиотек (например, `rich`).

## 3. Интерфейсы, которые нельзя ломать

| Интерфейс | Смысл |
|-----------|-------|
| `Equipment(...)` | одна запись; поля обязательные, состояние проверяется |
| `Equipment.to_dict()` | запись → словарь для JSON |
| `Equipment.from_dict(payload)` | словарь JSON → запись, `ValueError` при ошибке |
| `Inventory.all()` | список записей, отсортированный по номеру |
| `len(inventory)` | количество записей |
| `demo_inventory()` | источник данных спринта 1; в спринте 4 заменится загрузкой файла |

## 4. Проверка (демонстрация)

1. `python main.py` — появляется баннер и меню.
2. Пункт `1` — таблица из 8 записей, внизу «Всего записей: 8».
3. Пункт `2` — сообщение «появится в спринте 2», приложение не падает.
4. Ввод `abc` — сообщение «Такого пункта нет», меню повторяется.
5. Пункт `0` — корректный выход.

Критерии готовности спринта: меню запускается; проект открывается из
репозитория; демонстрационных записей не менее 5; запуск не требует
установки зависимостей.

## 5. Передача роли (для следующего LD / QA)

Готово: структура, модель, меню, просмотр демо-данных.

Не готово и не начато: добавление, поиск, изменение, удаление, JSON,
фильтры, автотесты.

Что делать в спринте 2:

1. `Inventory.add(values)` — проверка полей и уникальности номера
   (регистр не должен позволять дубль `pc-0001` и `PC-0001`).
2. `Inventory.next_number(kind)` — следующий свободный номер по префиксу
   (`PC-0003` для ПК).
3. Пункт меню `2`: ввод полей, повторный запрос при ошибке, запись в память.
4. QA: тесты на успешное добавление, пустые поля, повторяющийся номер.

Риск: при добавлении легко продублировать проверки между `main.py` и
`inventory.py`. Проверки должны жить в `inventory.py`, меню — только
спрашивать и показывать ошибки.
# Спринт 1 — инфраструктура, тестирование и окружение (роль QA / DevOps)

Документ фиксирует, что сделано за день, какие инженерные решения приняты и что нужно сделать следующему ответственному. Это часть сдачи QA / DevOps: «тест-кейсы и pytest-тесты, отчёт о проверках, контроль Git, инструкция запуска».

## 1. Границы спринта

Спринт 1 — развёртывание среды и базовый контроль качества. Настроены репозиторий, окружение и тестовый фреймворк `pytest`. Автотесты покрывают созданную модель данных и демонстрационный справочник (DoD спринта). Сценарии добавления, валидации ввода пользователя и проверки файлового хранилища зафиксированы в виде тест-кейсов на будущее, так как сами функции реализуются в спринтах 2–4.

## 2. Принятые решения

### Изоляция окружения и зависимости

- Создан `requirements.txt` с фиксацией минимальной версии фреймворка (`pytest>=7.0.0`).
- Проект рассчитан на работу в стандартном виртуальном окружении `venv`.
- В `.gitignore` добавлены шаблоны для исключения системных файлов, виртуальных сред (`venv/`, `.venv`), кэша байт-кода (`__pycache__/`), артефактов тестов (`.pytest_cache/`) и настроек IDE (`.idea/`, `.vscode/`), что исключает засорение репозитория платформозависимыми файлами.

### Безопасный импорт в тестах (`sys.path`)

Для предотвращения ошибок импорта вида `ModuleNotFoundError: No module named 'inventory'` при запуске тестов напрямую через IDE или отдельные расширения в начало тестовых модулей добавлена динамическая резолюция пути:
```python
ROOT_DIR = Path(__file__).resolve().parent.parent
if str(ROOT_DIR) not in sys.path:
    sys.path.insert(0, str(ROOT_DIR))
```
## 3. Что передаётся следующему QA / DevOps

### В репозитории оставлено в рабочем состоянии:
1. `tests/test_inventory.py` — базовый набор автотестов модели. Пути импорта настроены через `sys.path`, тесты запускаются как через `python -m pytest`, так и напрямую через IDE.
2. `requirements.txt` — зависимости проекта.
3. `tests/README.md` — зафиксированный протокол тестирования за Спринт 1.

### Известные ограничения и риски на данный момент:
* Пока нет тестов на добавление данных, так как метод добавления (`Inventory.add`) будет писаться Lead Dev только в Спринте 2.
* При добавлении записей в Спринте 2 есть риск появления дубликатов по инвентарным номерам при разном регистре (`pc-0001` vs `PC-0001`). Это нужно сразу закрыть тестом.
