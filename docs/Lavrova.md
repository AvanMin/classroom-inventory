Документ фиксирует, что сделано за день, какие инженерные решения приняты и что нужно сделать следующему ответственному. Это часть сдачи QA / DevOps: «тест-кейсы и pytest-тесты, отчёт о проверках, контроль Git, инструкция запуска».

## 1. Границы спринта

Спринт 1 — развёртывание среды и базовый контроль качества. Настроены репозиторий, окружение и тестовый фреймворк `pytest`. Автотесты покрывают созданную модель данных и демонстрационный справочник (DoD спринта). Сценарии добавления, валидации ввода пользователя и проверки файлового хранилища зафиксированы в виде тест-кейсов на будущее, так как сами функции реализуются в спринтах 2–4.

## 2. Принятые решения

### Изоляция окружения и зависимости

- Создан `requirements.txt` с фиксацией минимальной версии фреймворка (`pytest>=7.0.0`).
- Проект рассчитан на работу в стандартном виртуальном окружении `venv`.
- В `.gitignore` добавлены шаблоны для исключения системных файлов, виртуальных сред (`venv/`, `.venv`), кэша байт-кода (`__pycache__/`), артефактов тестов (`.pytest_cache/`) и настроек IDE (`.idea/`, `.vscode/`), что исключает засорение репозитория платформозависимыми файлами.

### Безопасный импорт в тестах (`sys.path`)

Для предотвращения ошибок импорта вида `ModuleNotFoundError: No module named 'inventory'` при запуске тестов напрямую через IDE или отдельные расширения в начало тестовых модулей добавлена динамическая резолюция пути:
```python
ROOT_DIR = Path(__file__).resolve().parent.parent
if str(ROOT_DIR) not in sys.path:
    sys.path.insert(0, str(ROOT_DIR))
```

# Спринт 2 —  роль Product Owner

Документ фиксирует, что сделано за день, какие продуктовые решения приняты и что нужно сделать следующему ответственному. Это часть сдачи Product Owner: «User Stories, критерии приёмки, задачи спринта, обновлённый README, протокол демонстрации».

## 1. Границы спринта

Спринт 2 посвящён реализации базового добавления и просмотра инвентаря с проверкой вводимых данных. Основной фокус направлен на контроль того, чтобы оборудование регистрировалось корректно (без дубликатов), а неверный ввод не приводил к аварийному завершению программы.

## 2. Принятые решения

### Структура данных и валидация

* **Поля карточки оборудования:** Утверждены обязательные поля — уникальный инвентарный номер, тип (ПК, монитор, принтер и др.), наименование, кабинет и состояние (исправно, требует ремонта, списано). Дополнительно могут фиксироваться дата поступления и ответственное лицо.


* **Уникальность:** Зафиксировано строгое бизнес-правило: система не должна позволять добавлять две записи с одинаковым инвентарным номером.


* **Устойчивость к ошибкам (Crash-free):** Согласовано поведение при неверном вводе (например, пустые поля) — программа должна корректно обрабатывать ошибку и выводить понятное сообщение для пользователя без вылетов.



### Тестовые наборы данных

* Подготовлены примеры корректных записей для демонстрации успешного добавления оборудования (согласно критериям приёмки).


* Сформированы наборы ошибочных данных (дубликаты номеров, незаполненные поля) для передачи QA / DevOps под разработку автотестов.

2. `README.md` — актуализировано описание реализованных функций и правил заполнения инвентаря.
