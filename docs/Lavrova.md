## 2. Принятые решения

### Сохранение неизменяемости модели (`frozen=True`) и обновление данных

Класс `Equipment` спроектирован как неизменяемый датакласс (`frozen=True`, `slots=True`). Чтобы исключить неконтролируемые мутации объекта «на месте» и сохранить целостность данных:

* Обновление записи в методе `Inventory.update()` реализовано через функциональный паттерн с использованием `dataclasses.replace`.


* Создаётся новый валидированный экземпляр `Equipment` с обновлёнными полями, который точечно замещает старый объект по индексу во внутреннем списке `_records`.

```python
updated_item = replace(item, **updates)
idx = self._records.index(item)
self._records[idx] = updated_item

```

### Разделение логики и CLI (Separation of Concerns)

Для обеспечения высокой тестируемости:

* Вся бизнес-логика манипуляции коллекцией вынесена в методы класса `Inventory` (`get_by_number`, `search_by_room`, `update`, `delete`). Они не содержат интерактивных вызовов `input()` и `print()`, что позволяет QA писать быстрые изолированные юнит-тесты на `pytest` без использования моков ввода/вывода.


* Интерактивный ввод, валидация пользовательских ответов, меню выбора подрежимов и форматирование карточек оборудования изолированы в функциях обработчиков `main.py` (`find_equipment`, `edit_equipment`, `delete_equipment`).



### Нормализация поисковых запросов и нечувствительность к регистру

* Метод `Inventory.get_by_number()` выполняет очистку от краевых пробелов и приведение к верхнему регистру (`.strip().upper()`), гарантируя нахождение записи независимо от регистра ввода пользователя (`pc-0001` находит `PC-0001`).


* Метод `Inventory.search_by_room()` реализует регистронезависимый поиск по подстроке (`target in item.room.strip().lower()`), позволяя находить технику как по точному номеру аудитории, так и по вхождению (например, «склад» или «101»).



### Безопасное удаление и валидация статусов

* В соответствии с критериями приёмки PO, в CLI-интерфейсе перед вызовом `Inventory.delete()` добавлен обязательный шаг подтверждения операции (`y/n`, `да/нет`) с предварительным выводом карточки удаляемого оборудования.


* При изменении состояния оборудования проверяется соответствие кортежу допустимых статусов `STATES` (`"исправно"`, `"требует ремонта"`, `"списано"`). Попытка передать некорректный статус вызывает `ValueError`, предотвращая загрязнение справочника невалидными данными.

## 2. Принятые решения

### Изоляция файловой системы в тестах

Для тестирования функций `load_inventory` и `save_inventory` из модуля `storage.py` используется встроенная фикстура `tmp_path`. Это гарантирует, что тесты:

* Не перезапишут реальный файл `data/inventory.json`.


* Будут выполняться в изолированной временной директории для каждого тест-кейса.
* Не оставят мусорных файлов в репозитории после завершения прогона.



### Стратегия проверки устойчивости хранилища

Написано 5 автотестов (`tests/test_storage.py`), покрывающих основные требования к хранению данных:

1. **Отсутствие файла:** Проверено, что при старте без файла `inventory.json` программа не завершается с ошибкой `FileNotFoundError`, а возвращает пустой справочник.


2. **Пустой файл:** Проверено корректное чтение файла размером 0 байт.


3. **Повреждённый JSON:** Проверено, что синтаксические ошибки в файле (`JSONDecodeError`) перехватываются безопасно. *В процессе тестирования была выявлена ошибка кодировки при чтении `utf-8` на ОС Windows, тест был оперативно исправлен добавлением явного указания кодировки.*


4. **Неверная структура:** Проверена устойчивость к валидному JSON, в котором отсутствует обязательный ключ `"records"`.


5. **Успешный цикл:** Проверено полное прохождение цикла: создание записи -> атомарное сохранение -> успешное чтение.



### Контейнеризация (Docker)

В соответствии с требованиями для QA/DevOps подготовлен `Dockerfile`.

* Выбран легковесный базовый образ `python:3.11-slim` для минимизации размера контейнера.


* Установлены переменные окружения `PYTHONUNBUFFERED=1` и `PYTHONDONTWRITEBYTECODE=1` для корректного отображения логов CLI в терминале и предотвращения создания кэш-файлов.
* В корень проекта добавлен файл `.dockerignore`, исключающий папки `venv/`, `tests/` и `.git/` из контекста сборки.
* Так как Docker-контейнеры по умолчанию изолируют файловую систему, в инструкции по запуску прописана команда монтирования volume (`-v $(pwd)/data:/app/data`), чтобы файл `inventory.json` сохранялся на хост-машине между перезапусками контейнера.

## 2. Принятые решения

### Стандартизация и расширение демонстрационного справочника (`DEMO_RECORDS`)

Согласно требованиям итогового комплекта сдачи, файл примеров инвентаря должен содержать не менее 10 записей. В модуле `inventory.py` кортеж `DEMO_RECORDS` расширен до 10 эталонных позиций за счёт добавления сетевого и периферийного оборудования (`UPS-0001` — ИБП, `SW-0001` — коммутатор). При первом запуске приложения без существующего `data/inventory.json` справочник автоматически инициализируется этими данными и сохраняется на диск.

### Финализация модульной архитектуры (Separation of Concerns)

В релизной версии закреплено строгое разделение ответственности между тремя ключевыми модулями без циклических зависимостей:

* **`main.py` (CLI-интерфейс):** изолирует пользовательский ввод/вывод, форматирование таблиц (`render_table`) и карточек (`print_equipment_card`), а также перехват прерываний терминала (`KeyboardInterrupt`, `EOFError`), не допуская утечки логики консольного ввода в бизнес-слой.
* **`inventory.py` (Доменная модель и бизнес-логика):** опирается на неизменяемый дата-класс `Equipment` (`frozen=True`, `slots=True`) с валидацией обязательных полей и статусов в `__post_init__`. Все мутации в контейнере `Inventory` выполняются контролируемо (обновление через `dataclasses.replace`), а поиск и фильтрация (`filter_by_room_and_state`) возвращают отсортированные по инвентарному номеру списки.
* **`storage.py` (Слой персистентности):** обеспечивает отказоустойчивую работу с `data/inventory.json`. Реализована защита от отсутствующего, пустого или синтаксически повреждённого JSON-файла, а также **атомарная запись** через промежуточный `.tmp`-файл с последующей заменой (`Path.replace()`), что исключает потерю данных при сбое во время сохранения.

### Зачистка технического долга и ревизия репозитория

* Проведена проверка слияния всех рабочих веток (`feature/*`, `fix/*`) в основную ветку `main` без конфликтов.
* Актуализированы строки документации (`docstrings`) во всех модулях до состояния финального релиза.
* Проверено соблюдение правил `.gitignore`: из индекса репозитория полностью исключены кэш интерпретатора (`__pycache__/`), артефакты `pytest`, виртуальное окружение и временные файлы хранения.
