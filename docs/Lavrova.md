Реализована строгая обработка ситуаций отсутствия записи. Код подготовлен для последующей бесшовной интеграции с модулем постоянного хранения в JSON в Спринте 4.

## 2. Принятые решения

### Сохранение неизменяемости модели (`frozen=True`) и обновление данных

Класс `Equipment` спроектирован как неизменяемый датакласс (`frozen=True`, `slots=True`). Чтобы исключить неконтролируемые мутации объекта «на месте» и сохранить целостность данных:

* Обновление записи в методе `Inventory.update()` реализовано через функциональный паттерн с использованием `dataclasses.replace`.


* Создаётся новый валидированный экземпляр `Equipment` с обновлёнными полями, который точечно замещает старый объект по индексу во внутреннем списке `_records`.

```python
updated_item = replace(item, **updates)
idx = self._records.index(item)
self._records[idx] = updated_item

```

### Разделение логики и CLI (Separation of Concerns)

Для обеспечения высокой тестируемости:

* Вся бизнес-логика манипуляции коллекцией вынесена в методы класса `Inventory` (`get_by_number`, `search_by_room`, `update`, `delete`). Они не содержат интерактивных вызовов `input()` и `print()`, что позволяет QA писать быстрые изолированные юнит-тесты на `pytest` без использования моков ввода/вывода.


* Интерактивный ввод, валидация пользовательских ответов, меню выбора подрежимов и форматирование карточек оборудования изолированы в функциях обработчиков `main.py` (`find_equipment`, `edit_equipment`, `delete_equipment`).



### Нормализация поисковых запросов и нечувствительность к регистру

* Метод `Inventory.get_by_number()` выполняет очистку от краевых пробелов и приведение к верхнему регистру (`.strip().upper()`), гарантируя нахождение записи независимо от регистра ввода пользователя (`pc-0001` находит `PC-0001`).


* Метод `Inventory.search_by_room()` реализует регистронезависимый поиск по подстроке (`target in item.room.strip().lower()`), позволяя находить технику как по точному номеру аудитории, так и по вхождению (например, «склад» или «101»).



### Безопасное удаление и валидация статусов

* В соответствии с критериями приёмки PO, в CLI-интерфейсе перед вызовом `Inventory.delete()` добавлен обязательный шаг подтверждения операции (`y/n`, `да/нет`) с предварительным выводом карточки удаляемого оборудования.


* При изменении состояния оборудования проверяется соответствие кортежу допустимых статусов `STATES` (`"исправно"`, `"требует ремонта"`, `"списано"`). Попытка передать некорректный статус вызывает `ValueError`, предотвращая загрязнение справочника невалидными данными.
